# Спецификация «Календаря звонков»

Внешнее поведение системы: сценарии, правила, данные, API, интерфейс и границы тестирования.
Источник правды для API — контракт [`api/main.tsp`](../api/main.tsp) (из него генерируются
[`api/openapi/openapi.yaml`](../api/openapi/openapi.yaml) и `frontend/src/api/schema.d.ts`).
Термины — [`GLOSSARY.md`](../GLOSSARY.md). Решения, из которых собран документ, —
[карта wayfinder](https://github.com/kolesbars/ai-for-developers-project-386/issues/2).

## 1. Роли

- **Владелец** — один, заранее заданный профиль (имя, описание, часовой пояс) из конфигурации сервера.
  Регистрации и входа нет: админская часть `/admin` открыта без защиты, ссылки на неё в интерфейсе
  Гостя нет.
- **Гость** — бронирует встречу без аккаунта и входа, указывая имя и email.

## 2. Сценарии

**Гость**
1. Открывает каталог `/`: Владелец (инициалы, имя, описание) и Типы встреч — название, описание,
   длительность.
2. Выбирает Тип встречи → страница записи `/book/{id}`: календарь Окна записи и Слоты выбранного дня.
3. Выбирает свободный Слот, вводит имя, email и (необязательно) комментарий, отправляет.
4. Попадает на страницу подтверждения `/booking/{bookingId}`, которая переживает перезагрузку.
5. Если время уже занято — видит сообщение о конфликте и обновлённое расписание, введённые данные
   сохраняются.

**Владелец**
1. Открывает `/admin` → «Предстоящие встречи»: Бронирования всех Типов встреч одним списком.
2. «Типы встреч»: список, копирование ссылки `/book/{id}`, создание нового Типа встречи
   (id, название, описание, длительность).

Отмена и перенос Бронирований, редактирование и удаление Типов встреч, уведомления, вход — вне рамок
(см. §10).

## 3. Правила расписания

| Правило | Значение |
|---|---|
| Часовой пояс Владельца | `Asia/Almaty` (UTC+5, без перехода на летнее время) — из конфигурации |
| Окно записи | 14 календарных дней **начиная с сегодняшнего** (дни D…D+13 по поясу Владельца), сдвигается с текущей датой |
| Рабочие часы | пн–пт 09:00–18:00 по поясу Владельца; суббота и воскресенье — без Слотов |
| Длительность Слота | равна длительности Типа встречи (15…240 минут, кратно 15) |
| Шаг стартов | общий для всех Типов встреч — 30 минут: старты только в :00 и :30 |
| Последний старт дня | 18:00 − длительность (встреча целиком помещается в Рабочие часы) |
| Сегодня | возвращаются только старты позже текущего момента, без дополнительного запаса |
| Статус Слота | `busy`, если `[start, start + длительность)` пересекается с любым Бронированием **любого** Типа встречи; иначе `available` |

**Интервалы полуоткрытые `[start, end)`.** Встреча может начаться в момент окончания предыдущей.
Пример при Бронировании 10:00–11:00:

| Запрос | Результат |
|---|---|
| 10:00–11:00 (тот же или другой Тип встречи) | отклонён — `409 slot_taken` |
| 10:30–11:00 (частичное пересечение, 30-минутный Тип) | отклонён — `409 slot_taken` |
| 09:30–10:30 (60-минутный Тип) | отклонён — `409 slot_taken` |
| 11:00–12:00 | принят — `201` |
| 09:00–10:00 | принят — `201` |

**Одновременные запросы.** Правило непересечения гарантирует БД (exclusion constraint по интервалу
или блокировка в транзакции), а не только проверка в коде: из N одновременных запросов на
пересекающееся время успешен ровно один, остальные получают `409 slot_taken`.

**Создание Бронирования допустимо только на свободный Слот Окна записи:** `startAt` должен быть
стартом из сетки текущего Окна записи для этого Типа встречи и быть позже текущего момента, иначе —
`422 slot_unavailable`.

## 4. Данные

**Тип встречи** (`MeetingType`)

| Поле | Правила |
|---|---|
| `id` | задаёт Владелец; `^[a-z0-9]+(-[a-z0-9]+)*$`, 2–40 символов; уникален, неизменяем |
| `name` | обязательно, 1–100 символов |
| `description` | необязательно, до 500 символов |
| `durationMinutes` | 15…240, кратно 15 |

**Бронирование** (`Booking`): `id` (UUID, выдаёт сервер), `meetingTypeId`, `meetingTypeName`,
`startAt`, `endAt` (= `startAt` + длительность, вычисляет сервер), `guestName`, `guestEmail`,
`comment?`, `createdAt`.

**Запрос Гостя** (`CreateBookingRequest`)

| Поле | Правила |
|---|---|
| `meetingTypeId` | существующий Тип встречи |
| `startAt` | UTC, старт свободного Слота |
| `guestName` | обязательно, 1–100 символов |
| `guestEmail` | обязательно, корректный email |
| `comment` | необязательно, до 500 символов |

**Профиль Владельца** (`Owner`): `name`, `bio`, `timeZone` (IANA). Аватара нет — интерфейс показывает
инициалы.

**Предстоящие встречи** — Бронирования с `endAt` позже текущего момента, по возрастанию `startAt`,
без пагинации (объём ограничен Окном записи).

## 5. API

Все пути под `/api`, JSON. Моменты времени — `utcDateTime` (ISO 8601 в UTC, `2026-11-12T05:00:00Z`).

| Метод и путь | operationId | Успех | Ошибки |
|---|---|---|---|
| `GET /api/health` | `getHealth` | 200 `Health` | — |
| `GET /api/owner` | `getOwner` | 200 `Owner` | — |
| `GET /api/meeting-types` | `listMeetingTypes` | 200 `MeetingType[]` | — |
| `POST /api/meeting-types` | `createMeetingType` | 201 `MeetingType` | 400, 409 `meeting_type_exists` |
| `GET /api/meeting-types/{id}` | `getMeetingType` | 200 `MeetingType` | 404 `meeting_type_not_found` |
| `GET /api/meeting-types/{id}/slots` | `listSlots` | 200 `Slot[]` — все старты Окна записи со статусом | 404 `meeting_type_not_found` |
| `GET /api/bookings` | `listUpcomingBookings` | 200 `Booking[]` — предстоящие | — |
| `POST /api/bookings` | `createBooking` | 201 `Booking` | 400, 404 `meeting_type_not_found`, 409 `slot_taken`, 422 `slot_unavailable` |
| `GET /api/bookings/{id}` | `getBooking` | 200 `Booking` | 404 `booking_not_found` |

### Формат ошибки

`{ "code": "<стабильная строка>", "message": "<текст на русском>", "fieldErrors": [...] }` —
`fieldErrors` только у `validation_failed`.

| Статус | `code` | Когда |
|---|---|---|
| 400 | `validation_failed` | поля не прошли проверку (длины, email, формат id, длительность) |
| 404 | `meeting_type_not_found` | нет Типа встречи |
| 404 | `booking_not_found` | нет Бронирования |
| 409 | `meeting_type_exists` | Тип встречи с таким id уже есть |
| 409 | `slot_taken` | пересечение с Бронированием, в т. ч. проигравший одновременный запрос |
| 422 | `slot_unavailable` | старт вне Окна записи / Рабочих часов / не на сетке :00/:30 / в прошлом |

### Примеры: создание Бронирования

```http
POST /api/bookings
{ "meetingTypeId": "consultation", "startAt": "2026-11-12T05:00:00Z",
  "guestName": "Мария Смирнова", "guestEmail": "maria@example.com", "comment": "Про контракт API" }
```

`201 Created`

```json
{ "id": "6f1c2d4e-0b7a-4a51-9a63-2f0d8f6c1e10", "meetingTypeId": "consultation",
  "meetingTypeName": "Консультация", "startAt": "2026-11-12T05:00:00Z", "endAt": "2026-11-12T06:00:00Z",
  "guestName": "Мария Смирнова", "guestEmail": "maria@example.com", "comment": "Про контракт API",
  "createdAt": "2026-11-11T13:20:00Z" }
```

`400 Bad Request`

```json
{ "code": "validation_failed", "message": "Проверьте поля формы",
  "fieldErrors": [{ "field": "guestEmail", "message": "Некорректный email" }] }
```

`409 Conflict`

```json
{ "code": "slot_taken", "message": "Это время только что заняли. Выберите другое." }
```

`422 Unprocessable Entity`

```json
{ "code": "slot_unavailable", "message": "Это время больше недоступно." }
```

## 6. Время в интерфейсе

- API отдаёт и принимает моменты в UTC; часовой пояс Владельца приходит в `GET /api/owner`.
- Гость и Владелец видят время **в часовом поясе браузера**; дни календаря группируются по
  локальной дате браузера; переключателя пояса нет.
- Рядом со Слотами и в подтверждении — подсказка: «Время показано в вашем часовом поясе (…).
  Владелец работает по времени Алматы, пн–пт 09:00–18:00».

## 7. Интерфейс

Визуальное направление: Mantine, `primaryColor: 'violet'`, `defaultRadius: 'md'`, системный шрифт.
Прототипы (выбрасываемые, для справки): ветки
[`prototype/guest-screens`](https://github.com/kolesbars/ai-for-developers-project-386/tree/prototype/guest-screens)
(вариант A) и
[`prototype/owner-screens`](https://github.com/kolesbars/ai-for-developers-project-386/tree/prototype/owner-screens)
(вариант A).

| Адрес | Экран |
|---|---|
| `/` | Каталог: Владелец и карточки Типов встреч с кнопкой «Выбрать время» |
| `/book/{id}` | Страница записи (две панели) |
| `/booking/{bookingId}` | Подтверждение |
| `/admin` | Админка Владельца |
| прочее | «Страница не найдена»; неизвестный Тип встречи — «Тип встречи не найден» |

**Страница записи `/book/{id}`** ([решение](https://github.com/kolesbars/ai-for-developers-project-386/issues/9))
- Слева — сводка: Владелец, Тип встречи, длительность, описание, выбранные день и время, подсказка о
  часовом поясе.
- В центре — сетка месяца (пн–вс) по дням Окна записи: дни со свободным временем подсвечены,
  выходные и дни без свободного времени серые и недоступны; по умолчанию выбран первый день со
  свободным временем.
- Справа — время выбранного дня: свободное — кнопка, занятое — зачёркнуто с подписью «занято» и
  недоступно; кнопка «Продолжить · 10:00–11:00» активна после выбора.
- Форма «Ваши данные» заменяет календарь и список времени, сводка остаётся; «← Другое время».
  Проверки полей — в браузере до отправки и на сервере.
- Конфликт (`slot_taken` / `slot_unavailable`): возврат к выбору времени, сообщение над списком
  («Это время только что заняли. Выберите другое — ниже актуальное расписание» /
  «Это время больше недоступно»), расписание перезагружено, данные формы сохранены.
- На узком экране панели идут друг под другом.

**Подтверждение `/booking/{bookingId}`** — «Вы записаны», Тип встречи, дата и время, подсказка о
часовом поясе, имя и email Гостя, «Добавить в календарь» (.ics), «Записаться ещё».

**Админка `/admin`** ([решение](https://github.com/kolesbars/ai-for-developers-project-386/issues/10))
- Боковое меню: Владелец (инициалы, имя, часовой пояс), «Предстоящие встречи» и «Типы встреч» со
  счётчиками, «Открыть страницу для Гостей ↗». На узком экране меню над содержимым.
- «Предстоящие встречи» (по умолчанию): лента по дням — время, бейдж Типа встречи, имя Гостя,
  email (`mailto:`), комментарий. Пусто: «Пока никто не записался. Поделитесь ссылкой на Тип встречи».
- «Типы встреч»: карточки (название, длительность, `/book/{id}`, описание, «Скопировать ссылку»),
  «+ Новый тип» открывает модальное окно.
- Форма создания: «Название»; «id (адрес страницы записи)» — подставляется из названия транслитом,
  редактируется, подсказка «Ссылка для Гостей: /book/{id} — изменить потом нельзя»;
  «Длительность, минут» (шаг 15); «Описание». Ошибки — под полями, `meeting_type_exists` — под id.

## 8. Тестирование

| Уровень | Инструмент | Что проверяет |
|---|---|---|
| Backend | `testApplication` на `Application.module()` + embedded PostgreSQL | правила Слотов (окно, выходные, часы, шаг, прошедшие старты, статусы), валидация, все коды ошибок, примыкание 10:00–11:00 / 11:00, частичное пересечение 10:30, пересечение разных Типов встреч, N параллельных `POST /api/bookings` на одно время → ровно один `201` |
| API (прямые запросы) | Playwright `request` против настоящего запущенного сервера | ключевые ответы по HTTP: `201` создания Типа встречи и Бронирования, `400 validation_failed`, `409 slot_taken`, `422 slot_unavailable`, `404` |
| Frontend | Vitest + Testing Library, `MantineProvider` + `MemoryRouter`, подмена `api` | состояния экранов: выбор дня и времени, занятые Слоты, ошибки полей, сообщение о конфликте с сохранением формы |
| E2E | Playwright в браузере; настоящие backend + frontend + PostgreSQL | Владелец создаёт Тип встречи → Гость бронирует → видит подтверждение → повторная попытка занять то же время → сообщение о конфликте → Владелец видит встречу в «Предстоящих» |

- **Текущее время**: backend берёт «сейчас» из внедряемого `Clock`; backend-тесты фиксируют время;
  API- и e2e-тесты работают на реальном времени и берут Слоты из ответа API, без захардкоженных дат.
- **БД без Docker**: если `DATABASE_URL` не задан, backend поднимает embedded PostgreSQL — так
  работают `mise run dev`, backend-тесты и e2e локально и в CI.
- Всё входит в `mise run check` (CI на каждый push).

## 9. Запуск и Docker

- Разработка: `mise run dev` (backend :8080 с embedded PostgreSQL + frontend :5173, Vite проксирует `/api`).
- Контейнер: многоэтапный `Dockerfile` (сборка frontend и backend, статика отдаётся Ktor) и
  `docker-compose.yml` с отдельным PostgreSQL (`DATABASE_URL`). CI собирает образ и проверяет, что
  контейнер поднимается и `GET /api/health` отвечает `200`. Локально Docker не обязателен.
- Конфигурация: `PORT` (запасной — `BACKEND_PORT`), `DATABASE_URL`, профиль Владельца (имя, описание, часовой пояс).

## 10. Вне рамок

Отмена и перенос Бронирований, редактирование и удаление Типов встреч, уведомления (email),
регистрация и вход, несколько Владельцев, переключатель часового пояса.
