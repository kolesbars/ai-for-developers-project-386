# Разбор референса calendar-ea8m

Вопрос (issue #3): как устроен референс https://calendar-ea8m.onrender.com/, какие экраны и сценарии есть
у Гостя и Владельца, какие данные он показывает и запрашивает, где слабые места UX и визуального дизайна
и что стоит улучшить в наших прототипах.

Дата разбора: 2026-11-11. Термины — по `GLOSSARY.md` (Владелец, Гость, Тип встречи).

## Источники и метод

Всё ниже — из первичных источников самого сайта, без пересказов третьих лиц:

- **[UI]** — живой сайт, пройденный в браузере (экраны 1280×900).
- **[JS]** — production-бандл `/assets/index-kyuaxNqY.js` (минифицированный React; роуты, тексты, логика форм).
- **[CSS]** — `/assets/index-DJozoOEh.css` (весь визуальный стиль, ~2 КБ).
- **[API]** — ответы GET-эндпоинтов (`/api/owner`, `/api/meeting-types`, `/api/meeting-types/{id}`,
  `/api/meeting-types/{id}/slots`, `/api/bookings`).

Ограничения: бронирования и Типы встреч **не создавались** (чужой сайт). Поведение POST-запросов и тексты
ошибок восстановлены по бандлу, а не по реальным ответам сервера. На момент разбора предстоящих встреч
было 0, поэтому список у Владельца виден только в пустом состоянии.

Практики Cal.com/Calendly ниже приводятся по общему знанию об их публичных страницах бронирования, без
отдельной сверки с их документацией в этом разборе.

## Карта экранов

Роутер (react-router) знает три пути, остальное перенаправляет на `/` [JS]:

| Путь | Экран | Для кого |
|---|---|---|
| `/` | Главная: Владелец + карточки Типов встреч | Гость |
| `/book/:meetingTypeId` | Выбор дня → времени → форма → экран «Вы записаны» (тот же URL) | Гость |
| `/owner` | «Страница владельца»: предстоящие встречи, Типы встреч, форма нового типа | Владелец |
| `*` | `Navigate to="/" replace` | — |

Ссылки на `/owner` в интерфейсе нет — страница открывается только прямым адресом [UI][JS].
Авторизации нет, вверху страницы Владельца жёлтая плашка: «Учебная страница без авторизации. Адрес доступен
всем, данные Гостей видны любому…» [UI][JS].

## Сценарий Гостя

### 1. Главная `/`

- Заголовок `h1` «Календарь звонков», ниже имя Владельца (`h2`) и bio из `/api/owner` [UI][API].
  Сейчас там заглушки: имя «Владелец календаря», bio «Выберите удобное время для встречи».
- Карточки Типов встреч: название, описание (необязательное), «N мин», кнопка-ссылка «Выбрать время» →
  `/book/{id}` [UI][JS]. Сетка `auto-fill, minmax(260px, 1fr)` от 640px, на узких экранах — один столбец [CSS].
- Состояния: «Загрузка…», ошибка с `role="alert"`, «Типов встреч пока нет» [JS].
- Сейчас в данных 2 типа: «Знакомство» 15 мин и «Консультация» 30 мин [API].

### 2. Выбор слота `/book/:id`

- Загружается Тип встречи (`GET /api/meeting-types/{id}`); при 404 — заголовок «Тип встречи не найден» и
  ссылка на главную. Тело 404: `{"code":"MEETING_TYPE_NOT_FOUND","message":"Тип встречи не найден"}` [JS][API].
- Шапка: название и «30 мин». Строка «Время указано в вашем часовом поясе: Asia/Almaty» — часовой пояс
  браузера Гостя (`Intl…resolvedOptions().timeZone`), выбрать другой нельзя [UI][JS].
- «Выберите день»: горизонтальный ряд кнопок-«чипов» с подписью вида «чт, 12 ноября» — только дни, где есть
  слоты. Выходные просто отсутствуют, без пояснения [UI][API].
- После выбора дня — «Выберите время»: сетка чипов «09:00 … 17:30». Выбранный день/время — синяя заливка,
  `aria-pressed="true"` [UI][CSS].
- Пустой ответ — «Свободного времени нет», ошибка — «Не удалось загрузить свободное время…» [JS].

Что видно из `/api/meeting-types/{id}/slots` (ответ — плоский массив `{startAt, endAt}` в UTC) [API]:

- Часовой пояс Владельца `Asia/Almaty` (из `/api/owner.timeZone`), рабочие часы 09:00–18:00, шаг стартов
  15 минут независимо от длительности (у 30-минутного типа 30 слотов в день, последний — 17:30).
- Только будни (пн–пт); окно — от завтрашнего дня по 24 ноября при «сегодня» 11 ноября, т.е. 14 календарных
  дней, включая сегодняшний (сегодняшние слоты отсутствуют — разбор шёл после 18:00 по Алматы).
- Для 15-минутного типа — 288 слотов на окно; всё приходит одним запросом, группировка по дням — на клиенте.

### 3. Форма «Ваши данные»

Появляется под сеткой времени только после выбора слота [UI][JS]:

- Поля: «Имя» (`autocomplete="name"`), «Email» (`type="email"`, `autocomplete="email"`). Больше ничего —
  ни комментария/темы, ни телефона.
- `noValidate` — клиентской валидации нет, ошибки полей приходят с сервера как `fieldErrors[{field, message}]`
  и мапятся `guestName→name`, `guestEmail→email`; поле подсвечивается `aria-invalid`, текст связан через
  `aria-describedby` [JS].
- Кнопка «Записаться» → «Запись…» на время запроса, защита от двойной отправки через `useRef` [JS].
- Запрос: `POST /api/bookings` с телом `{meetingTypeId, startAt, guestName, guestEmail}` [JS].
- Конфликты: `409` → «Это время уже занято, выберите другое», `422` → «Это время больше недоступно,
  выберите другое»; в обоих случаях выбор слота сбрасывается и слоты перезагружаются. Прочие ошибки — «Не
  удалось записаться. Попробуйте ещё раз.» [JS].

### 4. Подтверждение «Вы записаны»

Рендерится на том же URL вместо формы (без отдельного роута) [JS]. Список `dl`: Тип встречи, Дата
(«четверг, 12 ноября 2026 г.»), Время «10:00–10:30 (ваш часовой пояс: …)», Длительность, Имя, Email; кнопка
«Вернуться на главную» [JS][CSS].

## Сценарий Владельца `/owner`

- **Предстоящие встречи** (`GET /api/bookings`): кнопка «Обновить» (ручной refetch), список: название
  Типа встречи (или «Неизвестный тип встречи»), дата «чт, 12 ноября 2026 г., 10:00–10:30», «имя, email».
  Время — в часовом поясе Владельца, это подписано отдельной строкой. Пусто — «Предстоящих встреч нет» [JS][UI].
  Поля бронирования по бандлу: `id, meetingTypeId, startAt, endAt, guestName, guestEmail`.
- **Типы встреч**: маркированный список «**Название** N мин» + описание. Ни редактирования, ни удаления,
  ни скрытия [UI][JS].
- **Новый тип встречи**: «Название», «Описание» (textarea, необязательное), «Длительность, мин»
  (`type="number" step=15 min=15`), кнопка «Создать» → `POST /api/meeting-types`
  `{title, description?, durationMinutes}`; пустая длительность отправляется как `0`. Ошибки — серверные
  `fieldErrors` по полям `title|description|durationMinutes` [JS].
- Нет: отмены/переноса встреч, прошедших встреч, фильтров, настройки рабочих часов/часового пояса,
  редактирования профиля Владельца, ссылки «посмотреть как Гость» [JS].

## Эндпоинты API (видно по бандлу и сетевым запросам)

Клиент сгенерирован из OpenAPI (`@hey-api/openapi-ts`-подобный клиент: функции `get/post({url:"/api/…"})`) [JS].

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/owner` | `{name, bio, timeZone}` |
| GET | `/api/meeting-types` | `[{id, title, description?, durationMinutes}]` |
| POST | `/api/meeting-types` | создать Тип встречи |
| GET | `/api/meeting-types/{id}` | один Тип встречи, 404 `MEETING_TYPE_NOT_FOUND` |
| GET | `/api/meeting-types/{id}/slots` | `[{startAt, endAt}]` (UTC, ISO 8601) |
| GET | `/api/bookings` | предстоящие бронирования (без авторизации) |
| POST | `/api/bookings` | создать бронирование; 409 — занято, 422 — недоступно |

Ошибки — `{code, message}` и `fieldErrors[{field, message}]` для валидации [API][JS].

## Визуальный дизайн

Весь стиль — ~40 правил plain CSS, без UI-кита [CSS]:

- Фон `#f9fafb`, текст `#1f2937`, акцент `#2563eb` (Tailwind-палитра), системный шрифт, контейнер 960px.
- Только светлая тема (`color-scheme: light`), тёмной нет.
- Карточки — белые, `1px #e5e7eb`, радиус 8px; кнопки — радиус 6px.

## Слабые места и идеи улучшения

### Гость

1. **Нет «лица» Владельца.** Заглушки вместо имени/bio, нет аватара, `h1` — название сервиса, а не человека.
   Cal.com/Calendly начинают страницу с аватара, имени и короткого описания — это создаёт доверие.
   → Шапка профиля: аватар/инициалы, имя как главный заголовок, bio.
2. **Выбор дня — ряд из 9–10 чипов вместо календаря.** Выходные молча пропадают, границы окна
   (14 дней) не видны, непонятно, почему нет следующей недели. → Месячная сетка (как у Cal.com/Calendly):
   доступные дни активны, недоступные приглушены, вне окна — неактивны; подпись «запись на 14 дней вперёд».
3. **Длинная простыня времени.** 30–36 чипов при шаге 15 минут в 8–9 рядов. → Вертикальная колонка слотов
   справа от календаря (паттерн Cal.com), опционально переключатель 12/24ч; группировка «утро/день».
4. **Трёхэтажный экран без структуры.** День, время и форма идут сверху вниз в одну колонку на 960px, без
   сводки «что я выбрал». Кнопка «Записаться» далеко от выбранного слота. → Двухпанельная раскладка:
   слева сводка (Тип встречи, длительность, выбранные дата/время, часовой пояс), справа шаги; на шаге формы —
   выбранное время с кнопкой «Изменить» (как «Back» в Calendly).
5. **Часовой пояс нельзя сменить** и он показан идентификатором IANA (`Asia/Almaty`). → Селектор пояса
   с человекочитаемым названием и смещением (Cal.com/Calendly дают выбор пояса прямо над слотами).
6. **Форма слишком бедная и без клиентской валидации.** Нет поля «Комментарий/о чём поговорить»; ошибки
   приходят только после запроса. → Добавить необязательное поле заметки; базовая валидация до отправки
   (обязательность, формат email) при сохранении серверной.
7. **Конфликт слота (409/422) сбрасывает выбор**, форма исчезает (она видна только при выбранном слоте),
   а сообщение остаётся под сеткой; имя/email в состоянии сохраняются — это хорошо. Но экран резко
   «схлопывается», и Гость может не понять, что произошло. → Оставлять форму на месте с подсказкой
   «выберите другое время», подсвечивать соседние свободные слоты.
8. **Подтверждение на том же URL** — после перезагрузки страница возвращается к выбору слота, Гость
   теряет подтверждение. Нет «Добавить в календарь» (.ics/Google), нет указания, что делать дальше.
   → Отдельный экран/роут подтверждения, кнопки добавления в календарь, крупная иконка успеха.
9. **Карточки Типов встреч** не показывают ничего, кроме текста; кнопка во всю ширину одинаковая.
   → Иконка длительности, вся карточка кликабельна, hover-состояние (как список event types в Cal.com).

### Владелец

10. **Нет навигации и нет авторизации.** `/owner` доступен только по прямой ссылке и показывает
    персональные данные Гостей всем. → Хотя бы общая шапка с переключением «Публичная страница / Админка»;
    в нашем проекте — явно зафиксировать отсутствие авторизации как учебное допущение.
11. **Типы встреч только создаются.** Нет редактирования, удаления, скрытия, копирования публичной ссылки.
    → Карточки/строки с действиями «Изменить», «Копировать ссылку», «Скрыть»; форма создания — в модалке или
    отдельном экране, а не постоянно открытой внизу.
12. **Предстоящие встречи — плоский список с ручной кнопкой «Обновить».** Нет группировки по дням,
    нет «сегодня/завтра», нет отмены. → Группировка по датам (как Upcoming в Cal.com), бейдж Типа встречи,
    действие «Отменить»; автообновление при фокусе окна вместо кнопки.
13. **Мелочи формы.** Пустая длительность уходит как `0`; нет подсказки о допустимых значениях; нет выбора из
    пресетов. → Сегментированный выбор 15/30/45/60 + «другое».

### Визуальный дизайн

14. **Кнопки внутри форм с мелким системным шрифтом.** `.button` не задаёт `font`, поэтому «Записаться»
    и «Создать» выглядят меньше остального текста [CSS][UI]. → Единый компонент кнопки (в нашем стеке —
    Mantine `Button`).
15. **Слабая иерархия.** На главной три уровня заголовков подряд, страницы «висят» в левой части широкого
    контейнера, много пустого пространства, нет шапки/футера. → Центрированная карточка-контейнер, явная
    иерархия: профиль → типы; на бронировании — одна карточка с панелями.
16. **Нет тёмной темы и фирменного акцента** — стандартный Tailwind-синий. → Mantine theme с
    `primaryColor`, поддержка `prefers-color-scheme`.
17. **Состояния загрузки — только текст «Загрузка…»** (Render просыпается до минуты, и всё это время
    пусто). → Скелетоны карточек и слотов.

## Что взять в наши прототипы

- Контракт референса близок к нашему домену: `owner{name,bio,timeZone}`, Тип встречи
  `{id,title,description?,durationMinutes}`, слоты `{startAt,endAt}` в UTC, бронирование
  `{meetingTypeId,startAt,guestName,guestEmail}`, 409 на занятое время — разумная отправная точка.
- Хорошие решения, которые стоит сохранить: `aria-pressed` на чипах, `aria-invalid`/`aria-describedby` для
  ошибок, защита от двойной отправки, перезагрузка слотов после 409, подпись часового пояса на каждом экране.
- Главные точки улучшения для прототипов: календарная сетка + колонка слотов, сводка выбранного рядом
  с формой, отдельный экран подтверждения с «Добавить в календарь», выбор часового пояса, админка
  с навигацией и действиями над Типами встреч и встречами.
